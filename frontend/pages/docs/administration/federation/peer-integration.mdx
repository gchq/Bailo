# Federation and Peer Integration

Federation lets users of one Bailo instance discover models held in other Bailo instances or external model
repositories. For example, a user on Organisation A's Bailo instance can search the Marketplace and see which models are
available on Organisation B's Bailo instance, without needing an account on Organisation B's instance or leaving their
own instance to browse.

Each connected instance or repository is called a **peer**. This page explains how federation works. For step-by-step
configuration instructions, see [Setting Up Federation](setting-up-federation).

## How federation works

Federation is configured in the backend of each instance. There is no user interface for adding peers.

When a user searches the Marketplace and selects one or more external repositories:

1. Bailo searches the local instance and the selected peers
2. Each peer returns any matching models that the requesting identity is allowed to see
3. Bailo combines the results and identifies which peer each remote model came from
4. Users can then follow links to view remote models on the peer's own instance

The browser never talks to a remote peer's API directly. All federated searches go from one Bailo backend to the other,
so the local backend must be able to reach each peer over the network.

When a user selects a remote model in the Marketplace, they follow a link to that model on the peer's own website.
Viewing the model's full details, files and releases happens on the peer, under the peer's own access controls.

### What a remote instance shares

A Bailo peer answers federated searches through its normal search endpoint (`GET /api/v2/models/search`). Only search
results are shared: name, description, tags, organisation, state and similar summary fields. Model files, images and
releases are not transferred by federation.

Federated requests are subject to the remote instance's normal authentication and authorisation. The remote instance
only returns models that the requesting identity is allowed to see. That identity is either the calling instance's
service identity, or the original user if [user escalation](setting-up-federation#user-escalation) is turned on.

## Federation states

Each instance has an overall federation state, set in `federation.state`:

- **`disabled`** - Federation is turned off. No peer connections are created and the Marketplace does not show external
  sources. This is the default
- **`readOnly`** - Peer connections are created from the configured peers. Use this for an instance that mainly acts as
  a source for other instances, such as Organisation B in the example above
- **`enabled`** - Peer connections are created from the configured peers. Use this for an instance whose users search
  other instances, such as Organisation A in the example above

`readOnly` and `enabled` currently behave in the same way. The state is reported to other instances through
`GET /api/v2/system/status` so that peers can see how an instance is configured.

The federation state controls outgoing connections only. It does not stop other instances from querying your instance.
Incoming requests are controlled by your authentication and authorisation connectors, in the same way as any other API
request. See [Securing federation](setting-up-federation#securing-federation).

Each peer also has its own `state`, using the same three values. Setting a peer to `disabled` stops this instance from
checking whether that peer is reachable, without removing its configuration. A disabled peer still appears in the
**External repositories** filter, so remove it from `federation.peers` if users should not see it.

## Peer types

- **Bailo** (`bailo`) - Another Bailo instance
- **Hugging Face Hub** (`huggingfacehub`) - The public [Hugging Face Hub](https://huggingface.co) model repository

Hugging Face Hub peers only support plain text searches of at least five characters, and only return models, not data
cards. Searches that use other filters, such as organisation or state, return an error for that peer.

## How federation appears to users

When federation is turned on and at least one peer is configured:

- The Marketplace shows an **External repositories** filter listing each configured peer by its ID (the key used in
  `federation.peers`)
- Peers that the local backend cannot currently reach are marked as unreachable in the filter
- Selecting one or more peers includes their models in the search results alongside local models
- Each external model shows which peer it came from
- Selecting an external model opens it on the peer's own website
- If a peer returns an error for a search, such as an unsupported filter on Hugging Face Hub, the Marketplace shows the
  error above the results

If a selected Bailo peer cannot be reached at all, the whole search fails, including local results. Deselect the
unreachable peer to search again.

## Checking peer status

Bailo provides two system endpoints for federation:

- **`GET /api/v2/system/status`** - Returns this instance's federation `state` and `id`. Peers call this endpoint to
  check whether your instance is reachable
- **`GET /api/v2/system/peers`** - Returns each configured peer, its configuration and whether this instance can
  currently reach it

You can call both endpoints [via the API](../../../api/docs#/system).
